# 独立审核与对抗审核

两种审核,目的不同:

| | 独立审核 | 对抗审核 |
|---|---|---|
| 谁 | 没参与施工的 agent(同厂或异厂都行) | **另一家厂商**的顶级模型 |
| 审什么 | 一个 builder 的成品能不能合 | 方案、契约、切片成品 —— 挑刺、找漏、给替代 |
| 何时 | 每个 REQUIRES_REVIEW 的改动合并前;切片完成时 | 大决定定稿前(设计中途就拉);切片完成时 |
| 独立性来自 | 没参与施工、不读自证、不同上下文 | 没看过你的推理 |

---

## 一、独立审核

### 规矩

1. **只读**。审核者不改代码、不边审边修。
2. **不读 builder 的自证报告**。只拿:验收 ID、契约(含 AMEND)、目标 commit、构建指纹与环境。自证报告会把审核者的注意力引到 builder 想让人看的地方。
3. **自己做变异**。对每条关键断言,把它守护的那行生产代码删掉或改掉(真删行,注释掉不算 —— 有些哨兵 grep 注释照样命中),确认测试会红;报「变异 N/N 证红」。恒真断言是最常见的假绿。
4. **按生产接线端到端跑**。只在自检里生效的修复不算修复:确认生产路径真的走到了那段代码(常见形状:修复写在属性的 didSet 里,而生产里那个属性从没被赋过值,默认值不触发 didSet)。
5. **逐条定级**:PASS / FAIL / UNKNOWN + 证据 + 严重度。阻断 = 破坏验收、数据、隐私 / 权限、计费、发布条件。
6. **第一句就是结论**:能合 / 不能合。
7. 审核者给事实与定级,**裁定是领导者的事**:领导者读完写一份 AMEND(修订契约)或一句「放行」,不让审核者自己改方向。

### 审核简报模板

```text
推理档 high · 预计 <60> 分钟 · 退出条件:给出「能不能合」+ 阻断清单(带证据)。效率为主,预计只是预计,不是硬限。
你是独立审核者:只读;⛔ 不读 builder 的报告与提交信息里的自述;不改代码。
【对象】<worktree 路径> @ <commit>;对照基线 <commit>。
【契约】<CONTRACT-x.md> + <AMEND-1.md …>(冲突处以编号最大的 AMEND 为准)。
【验收 ID】<V1…Vn,各自的测试名>。
【重点】<这次的核心点:例如「账号边界」「迁移」「迟到回包」>。
【你要做】
  ① 逐条对照契约条目:实现了没有、生产路径是否真的走到(不只自检)。
  ② 对每条关键断言做变异(真删行),报 N/N 证红;没证红的每条写一句「哪一行坏了」。
  ③ 上一轮的阻断项逐条复核:已修并确认 / 部分 / 未修。
  ④ 这批 diff 有没有新回归(性能读数、迁移、默认开关)。
【输出】第一行「结论:能合 / 现在不能合」;然后 阻断 / 中 / 低 三档,每条:现象、证据(文件:行号 / 命令输出)、为什么是这个严重度;最后「已修并确认」清单与变异结果。
```

### 复审会收敛

整体审一轮之后,后面每轮只核「上一轮判 PARTIAL / FAIL 的那几条 + 这批 diff 有没有新回归」;把上一轮报告和 diff 一起喂,让审核者自己对照。窄范围复审每轮很快,几轮就能从「不放行」走到「放行」。

## 二、对抗审核:换一家模型

### 为什么换厂

同一家的模型容易和你的推理共享盲点。另一家的顶级模型没看过你的推理,是最硬的独立视角。它不只当收尾的审核员:**设计中途就拉它**,方案草稿先让它挑刺、找漏、提替代,再定稿。

### 做法(以一个通用的 CLI 形状为例)

```bash
# 把相关材料复制到一个干净目录,不让它整仓漫游
mkdir -p <审核目录>/ctx && cp <相关文件> <审核目录>/ctx/

# 只读沙箱 + 显式高推理;提示词从文件经 stdin 进入,输出与错误分开接
<外部模型 CLI> exec -m <模型名> -c model_reasoning_effort="xhigh" \
  -s read-only -C <审核目录>/ctx --color never - \
  < <审核目录>/prompt.md > <审核目录>/report.md 2> <审核目录>/stderr.txt
```

提示词要点:「反驳我、给替代方案、标出哪些是推断」;附上**相关文件清单 + 行号范围**,而不是整个仓库。

### 坑(每个都踩过)

1. **stdin 必须处理**:在 agent 的 Bash 工具里 stdin 常常是管道,CLI 会一直等 EOF。提示词走 `- < prompt.md`。
2. **stdin 只能重定向一次**:`… - < prompt.md … < /dev/null` 末尾那个会盖掉前面那个,CLI 报「没有提示词」空跑。
3. **默认推理档可能很低**:审核必须显式给高档;配置文件里不被新模型支持的项用 `-c` 覆盖掉。
4. **CLI 版本太旧**会拒绝新模型:先升级。
5. **不要在变异测试跑着的时候让它读仓库**:变异工具在反复改文件再还原,它审出来的全是假问题。先等变异进程退出,再确认没有备份残渣,才启动。
6. **撞到用量限额时报告是空文件**,stderr 里会写「几点再试」的具体时刻:按那个时刻重跑,别立刻重试。
7. **大仓库很贵**:整仓漫游一次能烧掉很大一块额度。只给相关文件的目录 + 行号范围。
8. **它的结论先自己对照代码事实**,再转给用户,不直接转贴。

### 结论怎么落地

- 对方案 / 契约的结论 → 领导者写 `AMEND-N`(见 `contracts-and-amendments.md`),冲突处以 AMEND 为准。
- 对成品的结论 → 进修复清单,按阻断 / 非阻断分。
- 分歧写进基调,由领导者定;用户拍板的照旧用户拍。

## 三、大批改动收尾:多镜头 + 反驳者

大批改动收尾时,可以编排一次多镜头对抗审核:

- 每个**镜头**是一个视角(并发、失败路径、隐私、计费、迁移、平台默认行为……),各派一个审核 agent 出发现。
- 每条发现再派 2–3 名**视角不同的反驳者**,要求「**拿不准就判不成立**」。
- 只有幸存的发现才修。经验上,存活率大约四成,而最严重的那条往往是领导者自己完全没看出来的。
- 几类反复抓到的 bug 形状见 `incident-lessons.md` 第二部分;开审前把它们发给每个镜头当检查单。
