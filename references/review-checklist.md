## 1 逻辑推理
- 方案回答的是基调里的目标,还是顺手长出来的?
- 每个状态转换有没有「说谎」的相(界面说的和系统在做的不一致)?
- 失败路径上用户看到的是事实,还是兜底文案?
- 对着状态表查:互斥条件、不可达状态、取消路径(不许凭感觉答「没有」)。
- 依赖的系统 / 私有 API / 第三方假设,是否对着真实环境证伪过?

## 2 用户使用与使用习惯(数据源 = 用户本人的实际使用;推测只能标 INFERENCE)
- 首次使用、日常第 100 次、出错那次,三条路各走一遍。
- 用户最常做的那一步:几次点按、几次等待、几次跳转?
- 记录用户**实际**停顿、误操作的地方。
- 不同语言的用户看到的是同一个产品吗?(把界面切到非母语走一遍:漏翻、截断、布局劈开只在那里现形)
- 和用户已经习惯的同类产品比,哪一步更重?

## 3 UI 设计
- 各语言截图逐页看过并绑定构建。
- 层级清楚:必需的操作找得到、不易误触。
- 空态 / 加载 / 错误三态可理解、可恢复(系统默认样式完全可以是最好的)。
- 文案说人话,不点供应商名、不带营销词。
- 深浅色、动态字号、长文本截断、读屏与焦点顺序看过一遍,失败截图留档。

## 4 功能性
- 基调里的用户可见验收,当场演示。
- 边界:空输入、超长输入、断网、权限被拒、被打断。
- 数据契约分别定义并验证:进程被杀 / 升级迁移 / 卸载清除 / 云端恢复 / 订阅恢复,各自该保留什么。
- 性能:关键路径的耗时有数字。
- 实际安装、走完整条路径的证据(不只是编译绿)。

## 5 服务器 / 云端
- 每条请求谁付钱、扣哪条额度、失败重试会不会双扣。
- 幂等、乱序、回包丢失三种情形都有处理。
- 密钥、令牌、用户数据不进日志、不进客户端明文。
- 用量和成本能按用户 / 按天看到。
- 服务端和客户端对同一规则(周期边界、额度、档位)只有一份真值。

## 6 多设备端
- 各端对同一状态说同一句话。
- 一边改了设置,另一边什么时候知道。
- 账号在多设备登录,额度与订阅怎么合并。
- 一台设备被杀 / 离线,另一台的界面会不会说谎。
- 新平台的功能缺口有没有明写,而不是静默少一块。

## 附 · 发布专项(按你的平台改写,放进对应维度用)
- CAPABILITY:每一步的调用者与所用的公开能力列清;私有能力标风险。
- ACCESS-MATRIX:权限未开 / 被拒 / 事后撤销 / 断网,各有可用的基础路径。
- LIFECYCLE:被杀、重建、锁屏、来电、切设备、取消后迟到回包、内存压力;电量与内存有读数。
- DATA-FLOW:原始数据 / 派生数据 / 诊断日志各去哪、留多久、怎么删;与商店隐私声明一致。
- RELEASE-PACKAGE:最终发布包里的扩展、签名、权限说明;至少一次真实分发配置下的安装验收;有账号就有 App 内删号。
- REVIEW-REPRODUCTION:商店审核员照说明从干净安装能复现;订阅覆盖购买 / 恢复 / 失效 / 跨设备。

只有阻断项(破坏验收、数据、权限、计费、发布条件)挡交付;不在 review 里现场修。
