# AMEND-1 · 笔记跨设备同步契约 v0.1 → v0.2(领导者 2030-01-15 晚;来源:对抗审核 `review/cross-vendor/report.md`,结论「修改」)

> **虚构示例**。与 `contract-example.md` 冲突处**以本文件为准**。范围不缩:同步这一版照做、照旧默认关。效率为主,预计只是预计,不是硬限。

## 合并与删除

- **M1 合并不用客户端时间**:服务端每次写入给行盖单调递增的 `rev`(bigint 序列);游标 = 已见的最大 `rev`。客户端每条 push 带 `base_rev`(它上次见到的该条的 `rev`,新条为 0)。服务端:行不存在 → 写;`row.rev > base_rev` → **服务端赢**(该行进 pull,客户端改本机);否则客户端赢。删除是墓碑,同样比 `rev` —— 离线设备的旧编辑盖不掉新删除。
- **M2 墓碑不过期**(永久保留,另计上限 10000);删掉 v0.1 的「30 天」。
- **M3 清空代次 epoch**:加表 `sync_state(user_id, epoch int)`。`DELETE /v1/notes/cloud` = 删该用户全部行 + `epoch + 1`。每个 sync 请求带 `epoch`;不符 → `409 {reason: "epoch_changed", epoch}` → 客户端**自动关同步**、清游标与待传队列、设置页说「云端副本已被清空,同步已关」;要再开必须用户重新打开开关(采用新 epoch,先 pull 再 push)。这样清空之后,别的设备和旧队列传不回来。

## 账号与载荷

- **M4 账号边界**:本机的游标 / 待传队列 / epoch / device_id 按 user id 分开存;登出或换账号 → 同步关、队列清。⛔ 上一个账号的笔记不许推给下一个账号。
- **M5 拉回来的不算本地修改**:导入时不改「最后修改时间」、不标脏 → 不回传、不循环。
- **M6 载荷最小化**:同步字段只留 `note_id, title, body, tags, pinned, deleted, base_rev`;⛔ 不传客户端时间;`device_id` = 每次安装随机生成的 UUID,与硬件无关,只用于「不把自己推的再拉回来」。

## 协议

- **M7 协议补全**:push 带 `op_id` 幂等(同 `op_id` 重放返回首次结果);pull 分页 ≤ 500 条 / 次,带 `more`;单次 sync 在一个事务里;超额返回 `413 {reason: "quota", limit}`,客户端停传并在设置页说明。
- **M8 服务端停用**:远程配置 `kill_notes_sync`,服务端拦(`503 {reason: "disabled"}`);客户端拉不到配置时照本机开关走,但服务端说停就停。

## 披露

- **M9 不是端到端加密**:设置页写明「笔记存在我们的服务器上,服务端可读;不是端到端加密。」⛔ 不许写「只有你能读」。端到端加密进候补,等产品负责人定。
- **M10 披露在数据第一次出机之前**:开关旁的确认页;事后的日志不替代它。

## 验收自检至少覆盖

迟到回包丢弃 · 换账号不串 · epoch 变了自动关 · 墓碑压过旧写 · 拉回不回传 · `op_id` 重放幂等 · 同步期间打字延迟不变。
